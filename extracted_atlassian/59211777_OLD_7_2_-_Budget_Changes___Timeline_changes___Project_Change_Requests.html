1. Purpose

This chapter defines how EZBuild handles project budget changes, timeline changes and project change requests after initial project bring-up. It outlines financial principles, supported scenarios, approval flows, and the impact on project financials, time and sales commissions.

The goal is to support real-world construction variability while maintaining financial transparency, governance, and traceability.

2. Core Financial Concepts

2.1 Project Budget Structure

Every project has a defined budget composed of:

  • Receivable (Customer Payments): Amounts billed to and collected from the customer.

  • Payable (Project Expenses): Internal costs, subcontractors, materials, labor, and other project expenses.

2.2 Milestone-Based Definition

  • Both receivables and payables are defined at the project milestone level during project bring-up.

  • Project-level financials are always a roll-up of milestone-level values.

  • Each milestone is defined with start date and end date. Actual end date is the date the milestone is completed according to this we’re evaluating project delays in milestone deliveries

2.3 Financial Calculations

From milestone data, the system calculates (defined in the project financial snapshot):

  • Total Project Receivable

  • Total Project Payable

  • Project Profit

  • Sales Commission (based on project and/or referral rules)

3. Budget and time Modification Scenarios

Budget changes can occur due to execution realities, scope changes, or commercial decisions. EZBuild supports the following scenarios.

3.a Unplanned Over-Budget or Timeline Overrun (No Approval)

Description
Actual payable, receivable, and/or execution time exceed the originally defined milestone plan without prior approval.

Rules & Behavior

  • No change is made to the original milestone budget or planned dates.

  • The milestone may be completed with:

    • Actuals exceeding planned financial values, and/or

    • Actual completion date exceeding planned milestone dates.

  • Variance is captured and reflected in:

    • Project financial calculations

    • Timeline tracking and reporting

    • Analytics and performance KPIs

  • No admin approval is required.

  • This scenario does not modify baseline expectations for budget or timeline.

  • Over-budget values and overdue milestones are visually highlighted (e.g., marked in red).

Use Case
Operational overruns, delays, or underestimations discovered only after execution.

3.b Planned Budget and/or Timeline Modification Within Existing Milestones

Description
A planned modification to budget and/or timeline within existing milestones, without changing the contractual scope.

Supported Changes

  • Planned increase to:

    • Payable (internal expenses)

    • Receivable (customer payments)

  • Planned modification to:

    • Milestone start and/or end dates

    • Overall project timeline (derived from milestone changes)

Budget and timeline changes may occur together or independently.

Rules & Behavior

  • Changes are updated directly in the milestone definition.

  • Budget updates affect financial rollups.

  • Timeline updates affect:

    • Milestone schedules

    • Project start/end dates

    • Timeline reporting and alerts

  • Project financials and timelines are recalculated automatically.

Approval Flow

  • Budget changes:

    • If exceeding the Financial Approval Threshold, require Admin approval.

  • Timeline-only changes:

    • Do not require admin approval by default.

    • Approval is required only of the project end date exceeds the planned end date.

    • Are fully audited and versioned.

  • Combined budget + timeline changes:

    • Follow the stricter rule (i.e., admin approval if financial threshold is exceeded).

Notes

  • Commission calculation logic remains unchanged.

  • No contractual addendum is created for this scenario.

3.c Project Addendum (Scope, Budget, and Timeline Change)

Description
The project scope is expanded by adding new milestones and formally modifying the project timeline and commercial terms.

A project addendum always includes a timeline modification.

Process Overview

  • A Project Addendum Form is created (design owned by Chen).

  • The form defines:

    • Additional milestones

    • Updated timeline for:

      • New milestones

      • Existing milestones (if impacted)

      • Overall project start and end dates

    • Customer receivable per milestone

    • Internal payable per milestone

    • Assigned salespeople

    • Commission method for this addendum

  • The addendum is:

    • Attached to the project contract

    • Treated as a contractual document

    • Shareable with the customer for signature and approval (online or offline; optional)

Approval & Customer Flow

  • Addendum requires Admin approval.

  • After admin approval:

    • It may be shared with the customer for approval, or

    • Marked as offline-approved by Sales

  • Only after approval:

    • New milestones are added to the project

    • Existing milestone dates may be adjusted

    • Project start/end dates are recalculated

    • Project financials and timelines are recalculated (see Section 4)

4. Sales Commission Handling for Addendums

Each addendum must explicitly select one of the following commission models.

Option I – Commission Aligned with Project Definition

  • Addendum receivable and payable are added to project financials.

  • Commission follows the standard project commission logic.

  • Lead cost follows the project definition (yes / no).

  • Fully integrated into project totals.

Option II – Commission Aligned with Sales Referral (Miscellaneous)

  • Addendum receivable and payable are not added to project financials.

  • Commission is calculated externally as a referral-based transaction.

  • No lead cost is applied.

  • A dedicated section appears in the financial snapshot:

    • Receivable

    • Payable

    • Commission

    • Profit

  • Section name: Miscellaneous

Option III – Net-Based Commission (Percentage of Profit)

  • Commission value is defined in the addendum form as a percentage.

  • Same structure as Option II (Miscellaneous section).

  • Commission calculation:

Commission = Percentage × (Receivable − Payable)

  • Commission is based on the net profit of the addendum milestones.

Option IV – Gross-Based Commission (Percentage of Payable)

  • Commission value is defined in the addendum form as a percentage.

  • Same structure as Option II (Miscellaneous section).

  • Commission calculation:

Commission = Percentage × Payable

  • Commission is based on gross payable, not profit.

5. Financial Snapshot Impact

Depending on the selected scenario:

  • Project-level financials may or may not be updated (in case of just a date change)

  • Addendum-related commissions may appear:

    • Inside project totals, or

    • In the Miscellaneous section

This separation ensures transparency between core project performance and external or referral-based compensation.

6. New Project for Existing Customer

6.1 Description

Instead of modifying an existing project, a new project may be created for the same customer.

6.2 Rules & Behavior

  • A full proposal and project setup is required.

  • Lead details are copied from the existing lead.

  • All project parameters must be redefined:

    • Milestones

    • Budget

    • Timeline

    • Salespeople

  • The new project is fully independent but linked under the same customer account and accessible accordingly.

6.3 Commission Handling

  • Sales commission is calculated as a referral.

  • No lead cost is applied.

7. Governance & Traceability

Across all scenarios:

  • All changes are auditable.

  • Original budgets remain traceable.

  • Approval decisions are logged.

  • Financial recalculations are automatic and deterministic.

This ensures trust, compliance, and operational flexibility within EZBuild.

8. Roles & Permissions

8.1 Roles Involved

Sales Person

  • Initiate addendums

  • Propose budget increases

  • Select commission models for addendums

  • Share addendums with customers (online or offline)

Project Manager (PM)

  • Identify unplanned overruns

  • Propose planned milestone budget increases

  • Validate payable estimates for addendums

Admin / GCC

  • Approve budget changes above threshold

  • Approve addendums before customer exposure

  • Configure company-level thresholds

Customer

  • Approve addendums that modify contract scope or price

9. Edge Cases & Exception Handling

Partial Approval

  • Addendums cannot be partially approved by default.

  • Admin may request changes and return the addendum to Draft status.

Customer Rejection

  • Rejected addendums:

    • Are archived

    • Do not impact project milestones or financials

Offline Customer Approval

  • Sales may mark customer approval as offline-approved.

  • Offline approval requires:

    • Reason

    • Optional attachment (e.g., signed document)

  • Admin visibility is mandatory.

Rollback

  • Once applied, addendums cannot be deleted.

  • Rollback requires a compensating addendum.

10. Audit & Reporting

  • All financial changes are versioned.

  • Original baselines are preserved.

  • Each approval includes:

    • Approver

    • Timestamp

    • Decision

Reports can distinguish between:

  • Baseline vs. actual

  • Project vs. miscellaneous commissions

11. Non-Functional Requirements

  • Deterministic financial calculations

  • No silent financial mutations

  • Role-based access enforcement

  • Full auditability

  • Scalability across multi-project portfolios
