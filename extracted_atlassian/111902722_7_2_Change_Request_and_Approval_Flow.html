1. Overview and Architectural Model

Change Requests (CRs) in EZBuild are not a standalone feature that users navigate to and fill in. They are an automatic interception layer that activates when a user attempts to modify a baselined project.

Once a project reaches Active status, certain edit actions — adding milestones, changing planned values, adjusting dates — are no longer direct writes. Instead, the system captures the intended change, holds it as a pending CR, and routes it for approval. The change is not applied to the project until the CR is approved.

This model has three implications for implementation:

  1. Existing milestone and project edit endpoints must detect baseline state and branch — direct write if pre-baseline, CR creation if post-baseline.

  2. The user experience of 'editing' a project must surface pending CRs inline — users should see what changes are held, not discover them elsewhere.

  3. The project's live data must remain pristine until approval. Pending CR values must not bleed into financial calculations, AI health scores, or customer-facing views.

 

The term 'Change Request' in this document refers specifically to post-baseline project modifications. Pre-baseline edits (during planning phase) are direct writes and do not create CRs.

 

2. Project Baseline — When CR Mode Activates

A project transitions into 'baselined' state when it moves to Active status. At this point the original milestone set, planned budget, and timeline become the reference against which all future changes are measured.

 

Baseline event

  • Triggered automatically when project status changes from Planning → Active.

  • The system snapshots the current milestones, planned values, and due dates as the original baseline. This snapshot is immutable and never overwritten by CRs.

  • Manually triggerable by GCC Admin before the status transition if needed (e.g. project started mid-migration).

4. CR State Machine

The state machine is identical for all CR types. The triggering edit action creates the CR directly in SUBMITTED state (skipping DRAFT) — the user's edit intent is the submission. For auto-approvable CRs, the transition to APPROVED happens in the same request cycle.

6. Customer Involvement

The customer's role in the CR process varies by CR type. For Budget and Timeline changes, the customer is an informed observer only if it impacts the project bounderies. For Scope (content) changes — additions, removals, or restructuring of milestones — the customer is an active participant whose acknowledgement is formally recorded. These changes requires Change or order addendum to be created and added to the project folder.

 

 

6.1  Scope CR — customer involvement (content changes)

A Scope CR represents a change to the agreed scope of work. This is the category most likely to affect the homeowner's expectations, timeline visibility, and contract. The following steps apply when a Scope CR is approved.

 

  1. System sends a 'Project scope updated' notification to the customer via their configured channel

  2. The Customer Portal surfaces a 'Pending changes' banner on the project overview until the customer acknowledges. This is read-only — customers cannot approve or reject CRs.

  3. The 'Contracts' section of the Customer Portal updates to reflect the new milestone set. If the company has 'Require customer acknowledgement on scope change' enabled in Settings, a formal acknowledgement action is presented (see §6.3).

  4.   The project's Activity feed in the Customer Portal shows the change event: what was added, removed, or modified — without exposing internal financial detail (no planned values, no commission data).

 

Customer-facing content in the Activity feed for a Scope CR must be scrubbed of internal financial data. Show milestone name changes and structural changes only. Planned values, budget deltas, and commission are not visible to the customer role.

 

6.2  Budget CR — customer visibility

Budget CRs are internal financial operations. Customers are not notified of budget changes by default. The exception is when a Budget CR affects a milestone that has already been presented to the customer on an invoice or payment schedule.

 

  • If the modified milestone has an associated AR invoice in Sent or Paid state, the GCC Admin is warned at approval time: 'This milestone has been invoiced. Verify with customer before proceeding.'

  • No automatic customer notification for Budget CRs unless the 'Require customer acknowledgement on scope change' setting is on AND the budget change accompanies a Scope CR.

 

6.3  Timeline CR — customer visibility

Timeline CRs that change a customer-visible milestone date trigger a date-change notification to the customer. This is informational, not requiring acknowledgement.

 

  • Auto-approved Timeline CRs: notification sent after approval.

  • Manually approved Timeline CRs: notification sent after approver approves.

  • The notification shows the milestone name and the old and new dates. No internal delay-cause information is included unless the GCC Admin adds a customer-facing note when approving.

7. Delegation

Delegation allows an approver to transfer their CR approval authority to another eligible user, preventing approvals from blocking when a key person is unavailable. Rules are identical to v1 of this spec; repeated here for completeness.

 Delegation is scoped: per CR type, per project, or global.

  • A delegate must hold a role that carries the required permission for the CR type being delegated. GCC Admin authority can only be delegated to another GCC Admin or GCC.

  • Mandatory expiry. Default maximum: 30 days if no end date specified.

  • Original approver can revoke at any time via Settings > Permissions > Approval Delegation.

  • Not transitive — delegates cannot sub-delegate.

  • All delegate approvals recorded as 'Approved by [delegate] on behalf of [original approver]'.

9. Financial Module Integration (§4.4.1)

All financial mutations happen atomically on CR transition to APPROVED. The CR service owns these transitions — no view or serializer should trigger them independently. Pending CR values must never appear in financial calculations.

 

On Budget CR approved

  1. New or modified milestones written to milestones table with classification = Change Request.

  2. Financial Snapshot recalculates: Plan column, Exercised vs Plan% across all rows.

  3. If the approved milestone value differs from an existing Completed transaction on that milestone, the auto-split logic (§4.4.1) evaluates.

  4. Commission applied at CR rate, not original project milestone rate. See §4.x — Commission.

 

Auto-split logic must only evaluate after the Budget CR reaches APPROVED. The pending CR value is not a committed transaction — do not trigger split logic during SUBMITTED or IN_REVIEW.

 

On Timeline CR approved

  1. Milestone and/or project end dates updated as specified.

  2. AI project health score re-evaluated.

  3. No financial figures change.

 

On Scope CR approved

  1. Milestones added, removed, or modified as specified in the CR.

  2. Original milestone baseline preserved as immutable read-only snapshot — never overwritten by subsequent CRs.

  3. Budget CR rules apply if any values changed simultaneously.

  4. Customer notification triggered per §6.1.
