Roles & Permissions Hierarchy

This document describes the complete EZBuild.AI Role‑Based Access Control (RBAC) model. Roles define access to modules, actions, data visibility, and approval authority. The permission hierarchy follows a strict top‑down model:

  1. System Admin – Full access to all system resources, internal tools, overrides, and support functions. Allocated and managed via Django admin. EZBuild support team.

  2. GCC – Company Owner with full company-level access including all modules, billing, templates, and role assignments.

  3. GCC Admin – Operations Administrator with broad access excluding billing, role hierarchy changes, and system‑level settings.

  4. Project Manager – Manages execution of assigned projects. Cannot view items outside their assignment.

  5. Sales – Manages leads, estimates, and conversions. Project visibility limited to assigned or created items.

  6. Subcontractor – Limited access to assigned project scopes, AP invoice submission, and compliance documents.

  7. Customer – Read-only access to their own project(s), invoices, and communication.

Role Hierarchy & Visibility Model
System Admin → GCC → GCC Admin → PM → Sales → Subcontractor → Customer

Visibility Levels:

·      View All: User can see all records across the organization.

·      View Assigned: User can only see records assigned directly to them (project, lead, task, invoice, etc.).

·      No Access: User cannot see or interact with the module.

Requirements and permissions allocation

  • Initial system is managed per role with the following defined role in the system (System admin is not defined in the system, it’s above the system):

    • GCC Admin

    • Sales

    • Project Manager

    • Sales & Project Manager

    • Sub Contractor

    • Customer

  • Change - Access, visibility and permissions shall be managed per functionality and per user and not per role. The roles should be used for only for the employee title, and should become free text field.

  • For each one of the system screens the user can be assigned one of the following permissions level:

    • No access - the screen or action is hidden, the user is not exposed to this relevant content.

    • View only - read only access.

    • Edit - the user can view, create and edit (he can’t approve content within this screen).

    • Approve - The user can create, edit and approve content within this screen.

    • Full control - except for approving the user can modify and delete content within a screen. for example, this user can delete uploaded contract in case these were uploaded by mistake.

  • Each screen there will be a checkbox (or other binary indication) which will flag if the user can see all the content or assigned content.

    • Example - In a customer office there’s complete separation between the sale department and project management:

      • Sales office admin can view all the leads in the office, and approve their proposal and contract, so the user permission in the lead will be set to Approve (or full control), and marked to view all content. The same user will have no access in the project management section.

      • The project management will have the same concept but in the opposite direction.

      • Leading sales man, is reliable and he can approve his own contracts - so in the leads he will be marked with approve permission, but he will view only his assigned leads and not all the leads.

  • The requirements above are generic to each one of the screen’s we have in the system. Apart from this generic requirement, each screen has specific fields that should have dedicated permission allocation in order to allow flexibility for different GCC.   • Additional requirements:

    • The difference between GCC and full control is the ability to control users and permissions.

    • GCC is allocated only per invitation to the system (first phase via django admin, later phase as part of system onboarding)

    • User permissions can be modified dynamically in order to enable delegation.

    • GCC should be able to delegate his permissions to other individual in the system, it should be as a separate section in the permissions called - GCC permissions delegation. this doesn’t remove the permissions from the original GCC.

    • The system should allow allocation of more than one GCC per company

  • All the requirements above are relevant for all the user access to the system - WebApp, Mobile App and ChatBot
