Req2 - Project planning process update

  1. User flow - Initiating new project from lead or from scratch. Planning the execution milestones and checklist. for each milestone planning the receivables and payables (not in every milestone we will have both or each), and shifting to project execution. Milestones can be added later in case these are missed, or in case we have change request / change of order / or direct customer sale like finish material which will be called “other”(see details in Req6).

  2. In the milestone section for each line in the table we should add Indication (Design) if this is from the original project contract or added on top of the original project contract (as change request or direct sale). This should be a label/icon for milestones coming from change request / change of order.

    1. Use case - during project execution additional milestones and project types are added, and the commission calculation should be evaluated differently (referral vs. non-referral vs. other).

    2. Each milestone which was migrated from lead, or added during the project planning phase should shouldn’t have this indication unless the lead itself is a referral, and each milestone which was added during project execution or new project type should have this by default.

    1. Each payable will open a financial line for this payable with all the details except for the actual payment.

In the payable section we have today 2 values - pending payables and completed payables. we should have 3 values - planned payables (as separate column - planned payable), pending payables and completed payables (like we have today). if payable is bigger than planned payable, mark the payable section in red.

    1. Customer receivables (redundancy on the financial snapshot).

    2. Miscellaneous.

    3. Finish Material.

    4. Reimbursement - see the details below.

  7. If milestone payables are bigger than receivable mark the payable in red. this can be a preplanned condition but it should still be marked in red.

Req3 - Commission Calculation and Override:

  1. Every team member (sales person and others) should have 3 fields of commission once they are added to the system.

    1. Office main lead cost – percentage field. This field represents how much commission the office takes from the sale (Net or Gross according to the company definition). Range 0%-100%, default value 15%.

    2. Office referral lead cost – percentage field. This field represents how much commission the office takes from the sale (Net or Gross according to the company definition). Range 0%-100%, default value 10%.

    3. Others lead cost - percentage field, assigned to all the receivable and deliverables tagged with “Other” field. most of the time the use case will be finish material and will have 0% lead cost on it.

    4. Sales commission ratio – the profit split between the sales person and the office. Always based on Net. Range 0%-100%, default value 50%.

  2. These fields should be editable in the team management (including GCC).

  3. Upon assigning sales managers to lead their commissions values should be added to the lead and and editable for that lead.

  4. When moving lead to project, the sales persons should be added to the project with their commission values from the lead or directly from the team Management in case it’s a new project or sales manager is added to the project.

  5. The commission values will be added to the finance to a new table which will be added to a new tab, visible only to GCC.

Req5 - Reimbursable and expenses:

  1. reimbursement is treated from the GCC point of view and the project point of view.

  2. The financial summary table should include column for aggregated receivables (“Receivables”).

  3. Reimbursement - GCC bought something for the customer. the customer returns the money to the GCC. Zero sum action (can be small profit here). New Source/Target is required. Payable = GCC paying for the customer, Receivable the customer returns money. It should be aggregated as a separate category as described in section e above.

    1. Important - the balance is managed in front of the customer.

    2. Future - if Payable > Receivables - add indicator.

  4. Future (not for now) - Expenses - Contractor or supplier is buying material / services for the GCC. This is just a payment management process, because eventually this expense is part of the normal project execution, it’s just “paid twice”. one time by the contractor and the other time by the GCC to the contractor (or supplier or team member). The way to manage this is by putting the first transaction as receivable by contractor/team member, The value should be added to the planned payments of this contractor and team member but the project sales price doesn’t increase. the payable process remains the same as normal payable, it’s aggregated as payable to this contractor/team member and project expenses increase regularly because money comes out of the project budget (while the GCC is paying back the original expense.

Req6 - Change request mini process:

  1. User flow - The project original planning was completed and shifted to execution. If a milestone was missed, the PM (or admin) can add it. There are cases in which the customer requests additional content. This content can be small and within the existing project, and it can be additional sub project within the same time. The process will be Change request or change of order after which contract addendum will be shared with the customer, and then additional milestones or sub project will be added to the system for execution. project closure will include both section. Important - the commission is different between the prepalnned project and the change of order.

  2. We will split implementation to include first the ability to support the change of order, and in later stage the full contract flow for it.

  3. Until we have this, we want to have short flow which will allow proper management of two use cases:

    1. change request content to the existing project type. adding new milestones. The flow is exactly the same as project planning phase, except that the default for each payable here is Change Request.

    2. New project type. This will be done in the project edit section, and all the milestones will be added as Change Request, and will be editable in the milestone tab.

    3. All the contract flow will be managed externally and added to the project as attachment (addendum).

  4. Permission to add new milestones / project type is aligned with the table permission.
